# Коннектор mitmproxy — дизайн

## Зачем

Через mitmproxy на NAS идёт трафик iPhone (Keenetic → HTTP/SOCKS5-прокси, позже WireGuard). Пользователь хочет:

1. **Видеть, куда ходят приложения** — на какие домены, сколько, с какими ответами. Это главное, что он делал руками в mitmweb.
2. **Подкладывать моки** — как на работе через MCP Proxyman: подменить ответ целиком или поправить поля настоящего ответа,
   формулируя задачу Claude обычными словами («подмени ответ `/v1/profile`: isPremium true»).

Образец по набору возможностей и поведению — MCP Proxyman (просмотр потока, деталь запроса, Map Local, Scripting, маскировка
секретов перед отправкой ИИ). Коннектор делается в Home MCP Hub по тем же правилам, что остальные (`CLAUDE.md`, «Структура»).

## Цели

- Сводка по доменам за период, с фильтром по приложению.
- Список запросов и один запрос целиком (заголовки и тела) — чтобы Claude видел структуру ответа перед моком.
- Моки двух видов: полная подмена ответа и правка настоящего ответа (поля JSON, статус, заголовки, задержка).
- Управление моками: список, выключить/включить, удалить, удалить все.
- Токены и секреты из перехваченного трафика не попадают ни к модели, ни в журнал хаба (по умолчанию).

## Не цели (пока)

- Map Remote, блокировка хостов, reverse proxy — родные опции mitmproxy, добавятся позже при надобности.
- Breakpoint / intercept: запрос висит, пока модель думает, — неудобно и рискованно.
- Повтор запросов (replay), правка и отправка запросов, экспорт `.flow`/HAR.
- Управление самим контейнером mitmproxy (запуск, режимы, сертификаты, `ignore_hosts`).
- Различение устройств (фильтр и имена по IP). Пока трафик идёт через Keenetic как клиент прокси, mitmweb, скорее всего, видит
  адрес роутера или docker-шлюза, а не телефона. Вернуться к этому после перехода на WireGuard.

## Анти-цели (провал, даже если «работает»)

- **Произвольный код от модели внутри прокси.** Никакого аналога `create_scripting_rule`: через прокси идёт весь трафик телефона
  со всеми сессиями, код от модели (или от вредной инструкции со страницы) мог бы их вывести. Моки — только декларативные правила.
- Утечка токенов в ответ инструмента, в журнал хаба или в логи pino при настройках по умолчанию.
- Моки, молча пропавшие после перезапуска контейнера mitmproxy.
- Мок, который незаметно продолжает работать: у каждого правила видно, включено ли оно и сколько раз сработало.

## Что уже есть (текущее состояние)

`Docker/mitmproxy/docker-compose.yaml` на NAS:

- образ `mitmproxy/mitmproxy:latest` (сейчас 12.3.x), `container_name: mitmweb`, сеть `fw` (dockfw), выход только в интернет;
- `mitmweb --mode regular@8080 --mode socks5@1080 --mode wireguard@51820 --web-host 0.0.0.0 --web-port 8081`,
  `--set web_password=${MITM_WEB_PASSWORD}`, `stream_large_bodies=1m`, `ignore_hosts`;
- `./scripts:/scripts:ro`, подключён аддон `-s /scripts/autoclear.py` — держит в памяти последние `autoclear_max` (3000) потоков.
  Истории на диске нет: всё, что видит коннектор, — эти последние N потоков в памяти mitmweb.

У хаба папка `Docker/` в коннекторе «Файлы» — только чтение.

## API mitmweb (проверено по исходникам 12.3.1, `mitmproxy/tools/web/app.py`)

- Авторизация: `Authorization: Bearer <web_password>` (или `?token=`); при успехе ставится подписанная cookie.
- `xsrf_cookies=True`: POST/PUT/DELETE требуют cookie `_mitmproxy_xsrf` и заголовок `X-XSRFToken` с тем же значением.
  Tornado принимает токен версии 1 (произвольная hex-строка), так что клиент может сгенерировать его сам и прислать оба.
- `GET /flows` — все потоки из view (JSON: `id`, `timestamp_created`, `client_conn.peername` = IP устройства, `request{method,
  scheme, host, port, path, headers, contentLength, timestamp_start}`, `response{status_code, headers, contentLength}`, `error`).
- `GET /flows/{id}/{request|response}/content.data` — тело.
- `POST /clear` — очистить список.
- `GET /options`, `PUT /options` (`{имя: значение}`) — опции, в том числе объявленные аддонами.
- `GET /state` — версия mitmproxy и режимы.

## Как устроено

```
iPhone → Keenetic → mitmweb (fw) ⇄ аддон hub_mocks.py
                       ↑ REST :8081, Bearer + XSRF
Claude → Hub (коннектор mitmproxy) — маскировка → ответ модели
```

### Аддон `hub_mocks.py`

Файл в репозитории хаба (например, `docs/mitmproxy/hub_mocks.py`), пользователь один раз кладёт его в `Docker/mitmproxy/scripts/`
и добавляет `-s /scripts/hub_mocks.py` в `command`. Аддон:

- объявляет опцию `hub_mocks` (строка JSON со списком правил) и `hub_mocks_rev` (номер версии правил от хаба);
- на `request` — правила «подмена целиком»: отвечает сам (`Response.make`), на сервер запрос не уходит;
- на `response` — правила «правка ответа»: меняет статус, заголовки, поля JSON по пути, добавляет задержку;
- помечает сработавшие потоки (`flow.comment` или `flow.marked`), чтобы в списке запросов было видно «под моком»;
- считает срабатывания по правилам и отдаёт счётчики через опцию только для чтения или через `flow.metadata`
  (точный механизм — на усмотрение исполнителя, лишь бы хаб мог прочитать счётчики через REST).

Аддон не выполняет присланный код и не читает файлы — только применяет данные из правил.

### Правило мока

- `id`, `name` (коротко, по-русски, для списков), `enabled`, `createdAt`.
- Совпадение: хост (точный или `*.example.com`), путь с `*` (без регулярных выражений), необязательный метод.
  Query в совпадении не участвует, если не указан явно. Правило действует для всех устройств, которые ходят через прокси.
- Вид `replace`: `status`, `headers`, `body` (строка или JSON), необязательная задержка. Разрешён для любых типов ответа, включая HTML
  (решение пользователя).
- Вид `patch`: `status?`, `setHeaders?`, `removeHeaders?`, `json` — список операций `{path, value}` (пути вида `user.isPremium`,
  `items[0].price`, `items[*].price`), задержка. Если ответ не JSON — правило с `json` пропускается и это видно в счётчике/ответе.

### Хранение и сверка

- Правила — источник истины в базе хаба (новая таблица), не в mitmproxy.
- **Желаемое состояние в прокси:** если коннектор включён и «Разрешить моки» включено — все включённые правила, иначе — пустой список.
  Так выключение моков или всего коннектора само снимает подмену трафика, без отдельного хука жизненного цикла.
- Хаб отправляет желаемый список в `hub_mocks` при каждом изменении правил и увеличивает `hub_mocks_rev`.
- **Фоновая сверка раз в минуту** (`node-cron`, стартует из `instrumentation.ts`, как скрипты): читает `hub_mocks_rev` и, если он
  не совпадает с желаемым (контейнер перезапущен и опции сбросились, коннектор выключили), отправляет список заново. Недоступный
  mitmweb — пропустить тихо (один warn в лог при смене состояния), без ошибок и без спама. Та же сверка — перед инструментами моков
  и в «Проверить».
- При выключенном коннекторе сверка читает его сохранённый конфиг (адрес и пароль), чтобы очистить правила; если конфига нет
  (коннектор удалён) — делать нечего.
- Если опции `hub_mocks` нет вовсе — аддон не подключён: понятная ошибка с инструкцией, как его положить и подключить.

### Маскировка секретов

Общий модуль (пригодится и camofox), применяется ко всему, что уходит модели из перехвата:

- заголовки `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key` и похожие (`*token*`, `*secret*`,
  `*session*`, `*auth*`) → `*** (N симв.)`; для `Cookie`/`Set-Cookie` имена cookies остаются, значения скрыты;
- query-параметры и поля JSON / form-urlencoded с именами вида `token`, `access_token`, `refresh_token`, `password`, `pass`,
  `secret`, `api_key`, `apikey`, `session`, `sid`, `code`, `jwt` → `***`;
- значения, похожие на JWT (`eyJ…​.​…​.​…`) и на длинные bearer-строки, в любом месте тела → `***`.

Переключатель в настройках коннектора «Показывать токены» (по умолчанию выключен) отключает маскировку для отладки.
Журнал хаба маскирует аргументы инструментов моков так же (тело мока может содержать токен, который пользователь сам вписал).

## Инструменты (рабочие названия)

Просмотр (всегда, read-only):

- `mitm_status` — версия, режимы, сколько потоков в памяти, подключён ли аддон, сколько правил активно.
- `mitm_hosts(minutes?, app?)` — сводка по доменам: домен, запросов, объём, коды ответов; приложение — по User-Agent
  (`AppName/1.2 CFNetwork/…`). Сортировка по числу запросов.
- `mitm_flows(host?, path?, app?, minutes?, limit?)` — метод, путь, статус, время, размер, флаг «под моком», `id`.
- `mitm_flow(id, offset?)` — заголовки и тела запроса и ответа после маскировки; длинное тело — по лимиту с `offset`, как в camofox;
  бинарное — только тип и размер.

Моки (за переключателем «Разрешить моки», по умолчанию выключен; без него инструменты скрыты через `hiddenTools`):

- `mitm_mock_replace(...)` — создать/обновить правило подмены целиком.
- `mitm_mock_patch(...)` — создать/обновить правило правки ответа.
- `mitm_mocks()` — список правил: что ловит, что делает, включено ли, сколько раз сработало.
- `mitm_mock_toggle(id, enabled)`, `mitm_mock_delete(id | all + confirm)`.
- `mitm_clear()` — очистить список перехвата (тоже за переключателем).

В ответе на создание правила — сколько уже перехваченных запросов подходит под шаблон (чтобы сразу было видно, что шаблон не мимо).

## Настройки коннектора

- Адрес mitmweb (по умолчанию `http://mitmweb:8081`), пароль веб-интерфейса (`secret()`).
- «Разрешить моки» (выкл.), «Показывать токены» (выкл.).
- Лимит текста в одном ответе (как «Лимит снапшота» у camofox), таймаут запроса.

## Ограничения

- Сеть: хабу нужен доступ к `mitmweb` по `fw` (`fw.allow.containers` у хаба), веб-порт уже слушает `0.0.0.0:8081`.
- Ответы инструментов короткие: Claude показывает их на телефоне.
- `stream_large_bodies=1m`: тела больше 1 МБ mitmproxy не сохраняет — в `mitm_flow` честно писать «тело не сохранено (стрим)».
- Префикс `mitm_` у всех инструментов (имена MCP глобальные).

## Решено пользователем

- Моки — оба вида: подмена целиком и правка полей настоящего ответа.
- Токены маскируются по умолчанию, переключатель «Показывать токены» выключен.
- Подмена целиком разрешена для любых ответов, включая HTML; правила действуют на всех устройствах.

## Решено мной (можно поменять)

- Маскировка включена по умолчанию, отключается переключателем — по образцу Proxyman.
- Моки — только декларативные правила, без кода.
- Правила живут в базе хаба и восстанавливаются после перезапуска mitmproxy.
- Шаблоны URL со звёздочками, без регулярных выражений.
- Map Remote, блокировка, breakpoint — не делаем в первой версии.
- Фоновая сверка раз в минуту; выключение моков или коннектора очищает правила в прокси.
- Различение устройств отложено до WireGuard.
- Управление правилами — только через Claude, отдельной страницы в админке в первой версии нет.
- Файл аддона кладёт пользователь вручную: `scripts/` смонтирован read-only, а папка `Docker/` у хаба тоже только на чтение.

## Оставлено исполнителю

- Точный формат JSON правил между хабом и аддоном, способ отдачи счётчиков.
- Как определять «приложение»: User-Agent, при его отсутствии — SNI/хост; группировка поддоменов в сводке.
- Набор имён полей для маскировки сверх перечисленного и эвристика длинных токенов.
- Схема таблицы правил и миграция Drizzle.
- Тесты: юнит на маскировку, сопоставление шаблонов, патчи JSON-путей, восстановление правил после «перезапуска»
  (мок REST mitmweb), скрытие инструментов моков; тест аддона на Python — желательно (mitmproxy `tflow`).
- Документация: раздел в `docs/connectors.md`, строка в `docs/security.md`, инструкция по подключению аддона.
